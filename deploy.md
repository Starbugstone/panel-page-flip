# Production Deployment Guide (FTP)

This guide takes the project from your **WSL2 Ubuntu** dev environment to a
**production server** that you can only reach over **FTP/FTPS** (typical shared
hosting). It uses only Docker on the dev side — you don't need to install Node,
Composer or PHP on your host.

> **Have SSH + git on the server?** Use [SSH-deploy.md](SSH-deploy.md) instead
> — it's faster, cleaner, and keeps secrets off your laptop. The same
> `scripts/.env.deploy` file drives both flows.

## TL;DR

```sh
# One-time setup
cp scripts/.env.deploy.example scripts/.env.deploy
$EDITOR scripts/.env.deploy        # fill in FTP_*, PROD_*, POST_DEPLOY_TOKEN

# Every release
./scripts/deploy.sh                # interactive: build → upload → migrate
# or step-by-step:
./scripts/build-release.sh
./scripts/deploy-ftp.sh
./scripts/post-deploy.sh
```

That's the headline. Read on for the full procedure, the first-time prep, and
the troubleshooting catalogue.

## 1. What gets deployed and where

The production server is laid out exactly like the local Docker stack:

```
<FTP_REMOTE_ROOT>/                          # this is your FTP user's home (or chroot)
└── backend/
    ├── bin/                                # CLI entry (php bin/console)
    ├── config/
    ├── migrations/
    ├── public/                             # **WEB ROOT** — point Apache/Nginx here
    │   ├── index.php                       # Symfony front controller
    │   ├── index.html                      # React app entry (from Vite build)
    │   ├── assets/                         # React JS/CSS (hashed filenames)
    │   ├── .htaccess                       # supplied by scripts/deploy/htaccess.dist
    │   ├── _post-deploy.php                # token-protected migration runner
    │   └── uploads/                        # USER CONTENT — preserved between deploys
    ├── src/
    ├── templates/
    ├── translations/
    ├── vendor/                             # composer install --no-dev (built locally)
    ├── var/
    │   ├── cache/prod/                     # pre-warmed during build
    │   └── log/                            # writable, tail it for errors
    ├── .env                                # the **committed** defaults
    ├── .env.local.php                      # secrets, generated by composer dump-env
    ├── composer.json
    └── composer.lock
```

**Important rules**:

1. Your FTP user must be **chrooted to** (or have its home set to) the directory
   that **contains** `backend/`. The web root the hosting panel points at is
   `backend/public/`.
2. `backend/public/uploads/` is **never touched** by deploys.
3. Secrets live only in `backend/.env.local.php` (a PHP file consolidated from
   `.env.prod.local` during build) — never in the committed `.env`.

### PHP version contract

Per project rule: **the production PHP version MUST match the Docker version**
(`PHP_VERSION` in `.env`, currently `8.2`). The build script uses
`php:${PHP_VERSION}-cli` to install Composer dependencies, so the binaries in
`vendor/` are guaranteed compatible with the prod runtime.

If your hosting upgrades to PHP 8.3, bump `PHP_VERSION` in the root `.env`,
rebuild and redeploy.

## 2. One-time setup

Do this once per workstation. After this, every deploy is three commands.

### 2.1 Create the deploy credentials file

```sh
cp scripts/.env.deploy.example scripts/.env.deploy
chmod 600 scripts/.env.deploy
$EDITOR scripts/.env.deploy
```

This file is **gitignored**. Fill in:

| Group           | Variables                                                                                                | Notes |
| --------------- | -------------------------------------------------------------------------------------------------------- | ----- |
| FTP target      | `FTP_HOST`, `FTP_USER`, `FTP_PASSWORD`, `FTP_PROTOCOL`, `FTP_PORT`, `FTP_VERIFY_CERTIFICATE`, `FTP_REMOTE_ROOT`, `FTP_PARALLEL` | Use `ftps` with certificate verification whenever the host supports it. |
| Public URL      | `PUBLIC_URL`                                                                                             | Used by `post-deploy.sh` to call the migration runner. |
| Post-deploy     | `POST_DEPLOY_TOKEN`                                                                                      | Run `openssl rand -hex 32`. **Same value** is baked into `backend/.env.local.php` as `DEPLOY_TOKEN` and used as the `X-Deploy-Token` header. |
| Symfony secrets | `PROD_APP_SECRET`, `PROD_APP_DATA_KEY`, `PROD_DATABASE_URL`, `PROD_FRONTEND_URL`, `PROD_CORS_ALLOW_ORIGIN`, `PROD_MAILER_*` | These are baked into `release/backend/.env.prod.local`, then consolidated into `backend/.env.local.php`. Preserve `PROD_APP_DATA_KEY` permanently or encrypted Dropbox credentials become unreadable. |
| Dropbox (opt)   | `PROD_DROPBOX_*`                                                                                         | Skip if you don't use Dropbox sync. |

Generate strong tokens:

```sh
openssl rand -hex 32   # use one for PROD_APP_SECRET, another for POST_DEPLOY_TOKEN
openssl rand -base64 32 # use once for PROD_APP_DATA_KEY; store it with backups
```

### 2.2 Verify Docker

```sh
docker version
docker run --rm hello-world
```

If `docker` is not in your PATH, install Docker Desktop on Windows and enable
the WSL2 Ubuntu integration.

### 2.3 First-time database creation on the host

You typically have one of these on shared hosting:

- A control panel (cPanel, Plesk, …) where you create the database, the DB user
  and grant privileges.
- A pre-provisioned DB whose credentials are emailed to you.

Whichever it is, take the resulting `mysql://USER:PASS@HOST:3306/DB` and put it
into `PROD_DATABASE_URL` in `scripts/.env.deploy`.

### 2.4 Configure DNS and the web root

In your hosting panel:

1. Point the domain at the directory that **contains** `backend/`.
2. Set the document root to `backend/public/`.
3. Enable HTTPS (Let's Encrypt is fine).

### 2.5 First deploy (only the very first time)

Run the workflow at least once *before any users exist* so you can:

- Confirm the FTP layout is what you expected.
- Hit `https://yourdomain.com/_post-deploy.php?action=health` (with the token
  header) and see PHP version, env, DB-connect status.
- Run `--action migrate` to create the schema.
- Create the first admin user via FTP-only post-deploy:
  - Either run the existing `app:create-admin-user` command via SSH (if you
    have it),
  - Or temporarily extend `_post-deploy.php` with an admin-create action (one
    extra `case` block calling the same console command) — remove it again
    once your admin exists.

## 3. The standard deploy workflow

Once you've done the one-time setup, every release is:

```sh
./scripts/deploy.sh
```

That wrapper asks "Build? Upload? Run post-deploy?" before each step.

For non-interactive releases (e.g. from CI):

```sh
./scripts/deploy.sh --yes
```

### What the wrapper does

1. **`scripts/build-release.sh`**
   - Cleans `release/`
   - Builds the React app inside `node:20-alpine` Docker image → `frontend/dist/`
   - Copies `frontend/dist/*` into `release/backend/public/`
   - rsync's `backend/` into `release/backend/` (excluding tests, dev env,
     uploads/, error.php, etc.)
   - Drops `release/backend/public/.htaccess` (Apache rewrite rules)
   - Drops `release/backend/public/_post-deploy.php` (token-protected)
   - Writes a temporary `release/backend/.env.prod.local` from your `PROD_*`
     vars
   - Runs `php:${PHP_VERSION}-cli` Docker image to:
     - `composer install --no-dev --optimize-autoloader --classmap-authoritative`
     - `composer dump-env prod` → produces `.env.local.php`
     - `bin/console cache:clear --env=prod`
     - `bin/console cache:warmup --env=prod`
   - Removes the plaintext `.env.prod.local` (its contents are now in
     `.env.local.php`)

2. **`scripts/deploy-ftp.sh`**
   - Pulls `minidocks/lftp` and runs `lftp mirror --reverse --continue` from
     `release/` to `<FTP_REMOTE_ROOT>` on the server
   - **Safe mode**: never deletes anything (`--delete` flag must be passed
     explicitly)
   - Excludes `.git*`, `*.log`, `node_modules/`, **`public/uploads/`**, etc.
   - Parallel uploads (default 3 connections)

3. **`scripts/post-deploy.sh`**
   - Calls `https://yourdomain.com/_post-deploy.php?action=health` with the
     `X-Deploy-Token` header
   - Then `?action=migrate` (runs Doctrine migrations)
   - Then `?action=cache-clear` (clears + warms the prod cache)

### Common variations

```sh
# Just rebuild
./scripts/build-release.sh

# Build only the frontend (skip composer install — fast, when only React changed)
./scripts/build-release.sh --skip-backend

# Build only the backend (skip the React build — when only PHP changed)
./scripts/build-release.sh --skip-frontend

# Push only the frontend (assumes backend is already in sync)
./scripts/deploy-ftp.sh --frontend-only

# Push only the backend (e.g. when only PHP changed)
./scripts/deploy-ftp.sh --backend-only

# See what would change without uploading
./scripts/deploy-ftp.sh --dry-run

# Manually trigger a single post-deploy action
./scripts/post-deploy.sh migrate
./scripts/post-deploy.sh cache-clear
./scripts/post-deploy.sh health
```

## 4. Manual fallback (no scripts)

If something is misbehaving and you need to do it by hand, here is the
equivalent step list.

### 4.1 Build the frontend

```sh
docker run --rm \
  -v "$PWD/frontend":/app -w /app \
  -u "$(id -u):$(id -g)" \
  node:20-alpine sh -c 'npm ci && npm run build'
```

→ produces `frontend/dist/`.

### 4.2 Build the backend release

```sh
mkdir -p release/backend
rsync -a --exclude='/var/' --exclude='/vendor/' --exclude='/tests/' \
      --exclude='/.env.local' --exclude='/.env.dev' --exclude='/.env.test' \
      --exclude='/public/uploads/' --exclude='/public/error.php' \
      --exclude='/public/index.html' \
      backend/ release/backend/

cp -a frontend/dist/. release/backend/public/
cp scripts/deploy/htaccess.dist release/backend/public/.htaccess
cp scripts/deploy/_post-deploy.php.dist release/backend/public/_post-deploy.php

cat > release/backend/.env.prod.local <<'EOF'
APP_ENV=prod
APP_DEBUG=0
APP_SECRET=...
DATABASE_URL=mysql://...
# (etc — see scripts/.env.deploy.example)
DEPLOY_TOKEN=...
EOF

docker run --rm \
  -v "$PWD/release/backend":/app -w /app \
  -u "$(id -u):$(id -g)" \
  -e APP_ENV=prod \
  php:8.2-cli sh -c '
    apt-get update -qq && apt-get install -y -qq git unzip libzip-dev libicu-dev libonig-dev libxml2-dev
    docker-php-ext-install -j$(nproc) zip intl pdo_mysql opcache
    curl -sS https://getcomposer.org/installer | php -- --install-dir=/usr/local/bin --filename=composer
    composer install --no-dev --optimize-autoloader --classmap-authoritative --no-interaction
    composer dump-env prod
    php bin/console cache:clear --env=prod --no-debug
    php bin/console cache:warmup --env=prod --no-debug
  '

rm release/backend/.env.prod.local       # secrets are now in .env.local.php
```

### 4.3 Upload via lftp

```sh
docker run --rm -i \
  -v "$PWD":/repo -w /repo \
  --entrypoint sh minidocks/lftp:latest -c '
    lftp <<LFTPEOF
    set ssl:verify-certificate no
    set ftp:passive-mode true
    open -u FTP_USER,FTP_PASSWORD ftps://ftp.yourdomain.com
    mirror --reverse --continue --parallel=3 --verbose \
       --exclude-glob "public/uploads/" \
       --exclude-glob "public/uploads/*" \
       --exclude-glob ".git*" \
       --exclude-glob "*.log" \
       release/ /
    bye
LFTPEOF
'
```

### 4.4 Run migrations & clear cache

```sh
TOKEN=$(grep ^POST_DEPLOY_TOKEN scripts/.env.deploy | cut -d= -f2-)
URL=https://comics.yourdomain.com/_post-deploy.php

curl -sS -H "X-Deploy-Token: $TOKEN" "$URL?action=health"
curl -sS -X POST -H "X-Deploy-Token: $TOKEN" "$URL?action=migrate"
curl -sS -X POST -H "X-Deploy-Token: $TOKEN" "$URL?action=cache-clear"
```

## 5. Post-deploy: migrations, cache & verification

### 5.1 Migrations

`POST $URL/_post-deploy.php?action=migrate` runs the equivalent of:

```sh
php bin/console doctrine:migrations:migrate --no-interaction --allow-no-migration --env=prod
```

Use `--allow-no-migration` so the call doesn't fail when there's nothing new.

### 5.2 Cache clear & warmup

`POST $URL/_post-deploy.php?action=cache-clear` runs:

```sh
php bin/console cache:clear --no-warmup --env=prod
php bin/console cache:warmup        --env=prod
```

This is mandatory after any change to `config/`, `src/Kernel.php`, attribute
routes, doctrine mapping, etc.

### 5.3 Verifying

After every deploy, hit each of these manually in a logged-out browser:

| URL                             | Expected                                                |
| ------------------------------- | ------------------------------------------------------- |
| `https://yourdomain.com/`       | React landing page loads (no 500, no blank screen)      |
| `https://yourdomain.com/login`  | Login form, can submit                                  |
| `https://yourdomain.com/api/me` | `401` while logged out (proves API + Symfony are up)    |
| `https://yourdomain.com/_post-deploy.php?action=health` *with header* | `200`, prints PHP version, `APP_ENV: prod`, `DATABASE_URL set: yes` |
| `https://yourdomain.com/_post-deploy.php` *without token* | `404` (proves the runner is locked down)                |

Then log in, upload one small CBZ, open it. If it renders, you're good.

## 6. Rollback

Because nothing is deleted on the server by default, rolling back is just
"redeploying the previous build".

### 6.1 Keep the last good `release/`

After every successful deploy:

```sh
mv release release-$(date +%Y%m%d-%H%M%S)
```

You'll end up with `release-20260507-2110/`, `release-20260507-2230/`, …

### 6.2 To roll back

```sh
rm -rf release
cp -a release-20260507-2110 release
./scripts/deploy-ftp.sh
./scripts/post-deploy.sh cache-clear
```

If the broken deploy added a migration and you need to roll the DB back too:

```sh
# Locally, find the previous version
docker compose exec php php bin/console doctrine:migrations:list

# Then on the server, via post-deploy with a custom action OR via SSH:
php bin/console doctrine:migrations:migrate VersionXXXXXX --env=prod
```

(You'll need to extend `_post-deploy.php` with a `migrate-down` action for this
case — keep it disabled by default.)

### 6.3 Emergency restore workflow

There's an existing `.github/workflows/emergency-backend-restore.yml` (mentioned
in `DEV_README.md`). It can be triggered from the GitHub UI to FTP-restore a
known-good backend snapshot. Configure the same secrets it expects.

## 7. What about the existing GitHub Actions workflow?

`.github/workflows/build-frontend.yml` already does **the frontend half**: when
a PR from `develop` is merged into `main`, it builds Vite and FTPs `dist/` into
`backend/public/`.

You have two integration patterns:

### Option A — keep both

Use GitHub Actions for the frontend (zero local effort), and run
`./scripts/build-release.sh --skip-frontend && ./scripts/deploy-ftp.sh
--backend-only && ./scripts/post-deploy.sh` from your machine for backend
changes.

This is fine but produces drift if the frontend's GH Action runs an older Node
than your script.

### Option B — single source of truth (recommended)

Disable the GH Action job and run `./scripts/deploy.sh` for every release.
Pros: identical PHP/Node versions to dev, deterministic builds, full control.
Cons: must run from a machine with Docker.

### Option C — extend the GH Action

Convert the workflow to call our scripts inside the runner:

```yaml
- name: Build release
  run: ./scripts/build-release.sh
- name: Deploy
  env:
    POST_DEPLOY_TOKEN: ${{ secrets.POST_DEPLOY_TOKEN }}
    FTP_HOST: ${{ secrets.FTP_SERVER }}
    FTP_USER: ${{ secrets.FTP_USERNAME }}
    FTP_PASSWORD: ${{ secrets.FTP_PASSWORD }}
    # …
  run: |
    ./scripts/deploy-ftp.sh
    ./scripts/post-deploy.sh
```

The runners on GitHub Actions have Docker, so the same scripts work unchanged.

## 8. Troubleshooting

### `lftp: 421 Sorry, cleartext sessions are not accepted` after `--protocol ftp`

Switch to `FTP_PROTOCOL=ftps`. Most hosting providers now reject plaintext FTP.

### `lftp: Fatal error: Certificate verification: …`

Either:
- Trust the cert chain locally (preferred), or
- Keep `set ssl:verify-certificate no` in `deploy-ftp.sh` (it's already on by
  default).

### `composer install` fails with "your php version (X) does not satisfy …"

The release was built with the wrong `PHP_VERSION`. Set it explicitly:

```sh
PHP_VERSION=8.2 ./scripts/build-release.sh
```

…and confirm it matches what the hosting actually runs (look at
`https://yourdomain.com/_post-deploy.php?action=health`).

### `_post-deploy.php` returns `404 Not found.`

- The token doesn't match. Confirm `POST_DEPLOY_TOKEN` in `scripts/.env.deploy`
  is identical to `DEPLOY_TOKEN` baked into the release. The build script
  takes care of this **only if** you ran the build *after* updating the env
  file.
- Or the script wasn't uploaded — check `release/backend/public/_post-deploy.php`
  exists, then re-run `deploy-ftp.sh`.

### `_post-deploy.php` returns `403 Refusing to run: APP_ENV is not 'prod'.`

`APP_ENV` got picked up from a stray `backend/.env.local`. Re-run the build —
the script removes that file from the release and produces `.env.local.php`
with `APP_ENV=prod`.

### `500 Internal Server Error` on `index.php`

Two likely causes on Apache shared hosting:

1. `mod_rewrite` isn't enabled — `.htaccess` rules silently fail.
2. `var/log/` and `var/cache/prod/` are not writable for the PHP user.

Fix #2 by setting permissions over FTP:

```sh
docker run --rm -i -v "$PWD":/repo -w /repo --entrypoint sh \
  minidocks/lftp:latest -c '
    lftp -e "
      open -u $FTP_USER,$FTP_PASSWORD $FTP_PROTOCOL://$FTP_HOST
      chmod -R 775 /backend/var
      bye
    "
  '
```

Or via SFTP/SSH:

```sh
ssh user@host "chmod -R 775 ~/backend/var"
```

### React app loads but `/api/...` returns the React `index.html`

The `.htaccess` is missing or `mod_rewrite` is off. Check the deployed
`backend/public/.htaccess` exists. If your host uses nginx, ask them to drop in
a config equivalent to `docker/nginx_frontend/nginx.conf`'s `location /api`
block.

### `frontend assets 404 after deploy`

Vite hashes asset filenames. If only `index.html` was uploaded but assets/
wasn't (or vice-versa), the SPA loads but JS 404s. Re-run with
`--frontend-only` to push `assets/` again.

### "I uploaded over my uploads folder by accident"

You can't, by design — both `build-release.sh` and `deploy-ftp.sh` exclude
`public/uploads/`. If you somehow bypassed both, see
[Section 6 Rollback](#6-rollback) and the emergency-backend-restore workflow.

### Mailer doesn't send on prod

- Check `MAILER_DSN` in `scripts/.env.deploy` (`PROD_MAILER_DSN`).
- Make sure the `Symfony\Component\Mailer\Messenger\SendEmailMessage` line in
  `backend/config/packages/messenger.yaml` is uncommented for prod if you want
  mail sent asynchronously (it is currently commented, so mailer runs sync).

### Database connection refused

- Most shared hosting requires connecting to `localhost` or `127.0.0.1` from
  PHP, not to the public DB hostname. Try both in `PROD_DATABASE_URL`.
- Check the DB user has the right host pattern (`%`, `localhost`, …).

### Migrations leave the DB in an inconsistent state

```sh
# From the post-deploy URL or via SSH
php bin/console doctrine:migrations:status --env=prod
php bin/console doctrine:migrations:list   --env=prod
```

If a migration is "executed but not registered" (because someone ran it
manually then changed the file), use:

```sh
php bin/console doctrine:migrations:execute 'DoctrineMigrations\\VersionXXXX' --up --no-interaction --env=prod
# or
php bin/console doctrine:migrations:version 'DoctrineMigrations\\VersionXXXX' --add --env=prod
```

## 9. Security notes

The deploy scripts apply some defaults. **Don't relax them without thinking.**

1. **`scripts/.env.deploy`** is `chmod 600` and gitignored. Keep it that way.
2. **`POST_DEPLOY_TOKEN`** is your remote-execution key. Treat it like an SSH
   private key. Rotate it whenever:
   - A team member with access leaves.
   - You suspect anything weird in `var/log/prod-*.log`.
   - On a fixed schedule (every 90 days is fine).

   Rotation procedure:
   ```sh
   # 1. New token
   NEW=$(openssl rand -hex 32)
   # 2. Update scripts/.env.deploy
   sed -i "s/^POST_DEPLOY_TOKEN=.*/POST_DEPLOY_TOKEN=$NEW/" scripts/.env.deploy
   # 3. Rebuild + redeploy (the new token is baked into .env.local.php)
   ./scripts/deploy.sh --yes
   ```

3. **The `_post-deploy.php` endpoint** only accepts the token via the
   `X-Deploy-Token` header (preferred) or the `?token=` query string (used as a
   fallback by old curl wrappers). The query-string variant is loggable in
   server access logs — prefer the header.

4. **HTTPS is mandatory** for the post-deploy URL. Without TLS your token is
   leaked over the wire on the first call.

5. **`backend/public/.htaccess`** ships with conservative security headers
   (HSTS, CSP, X-Frame-Options, X-Content-Type-Options) — see
   `scripts/deploy/htaccess.dist`. Adjust the CSP if you embed third-party
   scripts.

6. **Plaintext FTP is forbidden** in production (it sends your password and
   your release files in cleartext). The default protocol in
   `.env.deploy.example` is `ftps`. Use `sftp` if your host supports it (you
   may need to switch to a different docker image or a `--ssh` SSH workflow).

7. **Don't reuse `PROD_APP_SECRET` between staging and prod.** Generate a
   fresh one for each environment.

8. **Audit `backend/var/log/prod-*.log`** regularly for `_post-deploy.php`
   accesses. There's no reason for a stranger to know it exists.

9. **The `error.php` diagnostic page** that lives in `backend/public/error.php`
   in development is excluded by `build-release.sh` — make sure no one
   re-uploads it manually.

## 10. Reference: file inventory

| File                                              | Role                                                      |
| ------------------------------------------------- | --------------------------------------------------------- |
| `scripts/.env.deploy.example`                     | Template you copy to `scripts/.env.deploy`.               |
| `scripts/.env.deploy`                             | Your real credentials (gitignored).                       |
| `scripts/build-release.sh`                        | Builds `release/` from scratch using Docker.              |
| `scripts/deploy-ftp.sh`                           | Uploads `release/` to FTP via dockerized `lftp`.          |
| `scripts/post-deploy.sh`                          | Calls `_post-deploy.php` (or runs commands via SSH).      |
| `scripts/deploy.sh`                               | Wrapper that chains the three above.                      |
| `scripts/deploy/htaccess.dist`                    | Apache rewrite + security headers (copied to `public/.htaccess`). |
| `scripts/deploy/_post-deploy.php.dist`            | Token-protected migration / cache-clear runner. Copied to `public/_post-deploy.php`. |
| `release/`                                        | Generated, gitignored. Mirrored to the server.            |
| `release.tar.gz`                                  | Optional artefact for off-band uploads.                   |
| `backend/.env`                                    | Committed defaults only; never has secrets.               |
| `backend/.env.prod.local`                         | Generated locally, removed after `composer dump-env prod`. Never on the server. |
| `release/backend/.env.local.php`                  | Consolidated prod env (binary array). Lives on the server. |
| `release/backend/public/index.php`                | Symfony front controller.                                 |
| `release/backend/public/.htaccess`                | Apache rewrites + security headers.                       |
| `release/backend/public/_post-deploy.php`         | Token-protected post-deploy runner.                       |
| `release/backend/public/index.html` + `assets/`   | Vite-built React app.                                     |
| `release/backend/public/uploads/` *(server-side)* | User content. Never overwritten by deploys.               |

## Quick reference card

```
# Initial setup (once)
cp scripts/.env.deploy.example scripts/.env.deploy && chmod 600 scripts/.env.deploy
$EDITOR scripts/.env.deploy

# Standard release
./scripts/deploy.sh --yes

# Frontend-only hotfix (e.g. wording change)
./scripts/build-release.sh --skip-backend
./scripts/deploy-ftp.sh --frontend-only

# Backend-only hotfix (e.g. a small controller fix, no schema change)
./scripts/build-release.sh --skip-frontend
./scripts/deploy-ftp.sh --backend-only
./scripts/post-deploy.sh cache-clear

# Schema change (new migration)
./scripts/deploy.sh --yes
# (post-deploy.sh runs migrate + cache-clear automatically)

# Roll back
mv release release-broken-$(date +%H%M)
mv release-LASTGOOD release
./scripts/deploy-ftp.sh
./scripts/post-deploy.sh cache-clear
```

Good deploys, friend. Keep `release/` directories around until the next deploy
succeeds — they're cheap insurance.

## 11. Real-world notes from production deploys

Lessons learned the hard way, added 2026-08-06 after a panel-page-flip prod
deploy that exposed some silent-failure modes.

### Backup BEFORE pulling new code

The skill `panel-page-flip-deploy` (used on SSH/o2switch deploys) orders
backup → pull → composer → migrate → cache for a reason: backup captures
the **true pre-deploy state** (old code + old uploads + old env), so a
rollback is meaningful. If you pull first, the `cp -a ~/sites/comics
~/backup/...` snapshot includes the new code already, so a rollback
restores "new code + old uploads + old env" — not the actual pre-deploy
state. Don't reorder steps because the user phrases them casually
("pull, save, then deploy") — follow the runbook literally.

### SSH o2switch reality vs this FTP guide

This doc describes the FTP/docker build flow that works on **any**
hosting. For the actual `yourdomain.com` prod (o2switch shared
hosting with SSH access), the deploy is done over SSH using the
`panel-page-flip-deploy` skill, not this FTP flow. The FTP flow is still
useful as a fallback if SSH breaks; the SSH flow is faster, cleaner, and
keeps secrets on the server. See `SSH-deploy.md` §13 for the SSH/o2switch
deltas and the live runbook.

### `chown user:nobody` silently breaks if the user isn't in that group

On shared hosts (cPanel/LiteSpeed), webroot files should be owned by
`user:nobody`. If the SSH user isn't in the `nobody` group, `chown`
fails with "Operation not permitted" but doesn't error loud enough to notice.
 Combined with `chmod o-rwx`, you end up with files that nobody ("other")
can't read → 403 on every route, no entry in `var/log/dev.log`, only
LiteSpeed's `error_log` shows the requests. Verify with `groups` first;
fallback is `chmod -R u+rwX,g+rX,o+rX backend/public`.

### `_post-deploy.php` was removed in 2026-07

PR #51 changed the login endpoint from `/api/login_check` (GET only) to
`POST /api/login`. The `_post-deploy.php` runner still references the old
pattern in some error messages. If you see "login endpoint moved" type
errors from the runner, it's a runner bug, not a server bug — your prod
is fine.
